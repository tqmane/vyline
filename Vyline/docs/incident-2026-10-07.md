## 追加報告12: 通話記録のRange配信

### 確認した原因

- HAR 5/6/7で、非ゼロ位置へのRange要求に全体サイズの `Content-Length` を返していた。HAR 7の `bytes=720896-` は、本来561,512バイトのところ1,282,408バイトが保存され、本文先頭はMP4の `ftyp` だった。保存本文のSHA-256は提供MP4全体と一致した。
- 稼働サーバーのローカルHTTPへ同じ要求を送り、206・`Content-Range: bytes 720896-1282407/1282408` なのに全体1,282,408バイトを返すことを再現した。公開HARと直接配信は同じ誤った本文だった。Cloudflareを通る前から発生している。
- 稼働Bunは1.4.0。手元の同版でも、単純な `new Response(Bun.file(path).slice(start, end))` は正しいが、`new Response(response.body, response)` で再構築してHTTP配信すると範囲を失う。Honoのヘッダー統合とCORSを通す録画APIで同じ失敗を再現した。`slice().stream()` だけに変えても解消しなかった。

### 修正と検証

`backend/src/api/recordings.ts` と `backend/src/api/line.ts` の範囲配信を、`createReadStream(path, { start, end })` / `Readable.toWeb` に変更した。範囲全体をメモリへ読み込まず、HTTP応答の再構築後も指定位置だけを配信する。HEAD、空ファイル、不正範囲の416も維持する。BunがHTTP/1.1のストリームをchunked配信する場合は `Content-Length` がなくなるが、`Content-Range` と復号済み本文の範囲は一致する。

- 録画APIの回帰テストを、メモリ内 `app.request` だけでなくCORS付きの実 `Bun.serve` / HTTPへ拡張。全体・先頭・非ゼロ開始・終端指定・suffix・HEAD・416を検証。修正前は要求16バイトに全体1,282,408バイトの長さを返して失敗し、修正後はすべて成功。
- 通常添付キャッシュにも実HTTPの非ゼロRange検証を追加。録画ストア・WebDAVを含む関連テストは `bun test Vyline/backend/src/api/recordings.test.ts Vyline/backend/src/api/line.videoCache.test.ts Vyline/backend/src/storage/callRecordingStore.test.ts Vyline/backend/src/storage/recordingWebDav.test.ts` で **11成功・0失敗**。
- `apps/desktop/scripts/check-recording-range.ts` を追加。隔離した `tests/serve-call-recordings.ts` へローカルMP4を投入し、実際の一覧内プレイヤーとMP4を直接開く新タブで各3回検証する。ブラウザの非ゼロRange要求、元ファイルとのバイト一致、中間位置へのシーク、終端、デコード済みフレーム、エラーなしを確認。
- 提供MP4は全6回 **28.282033秒**、生成したfragmented MP4は全6回 **28.2885秒**。保存コピーは隔離fixture内に置き、検証後に削除した。実データ・録画画像はリポジトリへ追加していない。
- 既存録画harnessのMP4再生もBlob URLから実URLへ変更し、Range検証を先頭16バイトだけから非ゼロ範囲のバイト一致へ変更した。古い `window.confirm` モックは現在の同意状態・承認操作に合わせた。M4A/MP3/MP4の保存・再生・削除、自動録画の入退室・停止・アカウント切替、音声ミックス・ミュート・終話フラッシュまで成功した。
- backend / desktopの型検査、root lint、`git diff --check` は成功。

公開URLへの新規取得は認証リダイレクトになったため、公開側は提供HARを根拠とする。修正版の本番反映と公開URLでの再確認は未実施。サーバーで行った操作は既存APIのGET、コンテナ情報とBun版の読み取りのみ。
