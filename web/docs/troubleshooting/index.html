Troubleshooting

最初に「Browser / backend / filesystem / Docker / network / LINE protocol」のどこで止まっているかを分けます。複数の層を同時に変えると原因が見えなくなります。

最初の4コマンド

docker compose ps
docker compose logs --tail=200
docker compose config
docker inspect <vyline-container>

container の状態、実際に展開された Compose、mount、port、environment を確認します。設定ファイルに書いた値ではなく、running container の値を見ます。

Container が unhealthy / 起動しない

Dockerfile の healthcheck は container 内の http://127.0.0.1:3000/healthz を確認します。

docker compose logs --tail=200
docker inspect <vyline-container>

起動直後は healthcheck の start period があります。継続して失敗する場合は、backend の例外、/app/data / /app/storage の書き込み、port の競合を順に確認します。

pull したのに挙動が古い

image を pull しただけでは running container は置き換わりません。

docker compose pull
docker compose up -d
docker compose ps

Portainer でも pull 後に Stack の update / redeploy が必要です。

復元した履歴が再起動後に消える

UI で一度見えたことより、DB が永続化先へ書けたかを先に確認します。

  1. /app/data が期待する host path へ mount されているか。
  2. その path が空の別 directory に変わっていないか。
  3. backend が write error を出していないか。
  4. disk full / read-only filesystem ではないか。
docker inspect <vyline-container>
du -sh data storage
df -h .
docker compose logs --tail=200

詳細は 永続化 を参照してください。

localhost では開くが別端末から開けない

  1. VYLINE_BIND_ADDRESS と実際の published port を確認する。
  2. host firewall で必要な LAN から到達できるか確認する。
  3. VYLINE_LAN_ACCESS を用途に合わせて確認する。
  4. reverse proxy / VPN を使う場合は前段から origin への接続を分けて確認する。

0.0.0.0 で listen していることと、Vyline の remote access policy が許可していることは別です。

Cloudflare / reverse proxy では開くが操作できない

まず origin へ直接接続した場合と比較します。その上で Access policy、proxy header、WebSocket、VYLINE_LAN_ACCESS、VYLINE_TRUST_REMOTE_OWNER を確認します。

remote owner trust は「とりあえず直す」ために有効化せず、前段の認証境界が成立している場合だけ使います。

Android host だけ network が壊れる

Vyline container を止めて、まず plain container で確認します。

docker run --rm alpine ping -c 1 1.1.1.1
docker run --rm alpine ping -c 1 google.com

ip rule
ip route show table main
iptables --version
iptables -t nat -S
iptables -S FORWARD

IP 通信、DNS、published port を別々に確認します。Android/netd の既存 rule を一括 flush しないでください。詳しくは Android Network。

Android chroot で docker exec の中身がおかしい

real chroot の一部環境では docker exec が container 本体と異なる mount namespace を見る検証例があります。container PID の root を host から確認します。

PID=$(docker inspect -f '{{.State.Pid}}' <container>)
ls -la "/proc/$PID/root/app"

docker exec だけを根拠に image の filesystem が壊れたと判断しません。

開発時に import / package が見つからない

git submodule status
git submodule update --init --recursive
bun install --frozen-lockfile
bun run vyl:doctor

@vyline/protocol、Plugin、Themes、Tools は submodule です。pointer が未取得のままでは root workspace だけ install しても揃いません。

Docker / backend は正常だが LINE 操作だけ失敗する

この段階で初めて protocol / LINE 側を調べます。対象機能を RPC_DICTIONARY で引き、必要なら Desktop evidence と差分を確認します。

bun run vyline:check
bun run vyline:find-native -- <name>
bun run vyline:delta

session、device mode、E2EE key、RPC path のどれかを一度に全部変更せず、ログと失敗 endpoint を見て対象を絞ります。

Issue に残す情報

  • Vyline version / image tag
  • host OS と architecture
  • Docker / Compose version
  • 再現手順
  • 秘密情報を除いた関連 log
  • Docker の問題か LINE 機能の問題かの切り分け結果
token、session、E2EE key、backup、account DB を貼らない

診断に必要な値だけを残し、秘密情報は必ず除外してください。
