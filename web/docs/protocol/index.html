Internals

Protocol / E2EE

Vyline/packages/protocol は @vyline/protocol として使う独立 submodule です。LINE の login、transport、RPC、E2EE、OBS と Desktop 互換処理を担当します。

Repository と依存関係

submodule の実体は tqmane/vyline-api です。Thrift 型は workspace の @vyline/line-types / @vyline/loose-types を利用します。@evex/linejs はメソッド名や構造を調べる参考元であり、Vyline の runtime dependency ではありません。

Device mode

値扱い
IOSIPAD既定。副端末として公式 Desktop / smartphone との併存を狙う mode
ANDROIDSECONDARY副端末の代替 mode
DESKTOPWINWindows Desktop の header / login patch を使う互換調査用 mode
DESKTOPMACMac Desktop mode

通常は既定の IOSIPAD から始めます。Desktop mode は公式 Desktop と session が競合する可能性があるため、目的がないまま変更しません。

Login

Protocol package は QR、Email、Token の login path を持ちます。Desktop mode では Desktop と同じ endpoint / header に合わせる patch が入ります。Token 復元でも transport と E2EE identity の準備を通します。

login だけを UI から直接実装せず、client / protocol の既存 path を使うことで device identity と E2EE preparation を揃えます。

E2EE

Desktop key import、server 上の最新 key との整合、Letter Sealing の送受信を protocol と backend で分担します。ログイン前の過去メッセージは、対応する過去 key がなければ復号できない場合があります。

E2EE key は秘密情報です

desktop-e2ee-keys.json などの key dump は Git、Issue、公開ログへ入れないでください。

RPC を調べる

新しい LINE 機能や既存機能の破損を追うときは RPC_DICTIONARY を入口にします。

  1. linejsName または機能名を rpcMap.ts で検索する。
  2. desktopEvidence で Desktop 側の根拠を見る。
  3. 低レベルの stackApi を確認する。
  4. domainApi と backendApi へ上がる。

Desktop 更新時は bun run vyline:delta や bun run vyline:find-native -- <name> を使い、推測だけで RPC path を変更しません。

Transport

Talk、login、RSA などは用途ごとに endpoint が分かれます。これらは Desktop evidence と protocol の patch 実装を正本として扱い、Web Docs に endpoint 一覧を複製しすぎないようにします。

機能を追加するとき

まず modules.map.ts と RPC_DICTIONARY で既存の調査・実装位置を確認し、必要なら Desktop evidence を追加します。その後、低レベル stack → domain facade → backend service → HTTP route の順に接続します。

全体の責務は Architecture、repository 境界は Submodules を参照してください。
